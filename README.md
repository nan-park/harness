# harness

**Claude Code가 사용자의 의도에서 벗어나지 않게 잡아두는 개인용 하네스.**

AI 코딩 에이전트에게 일을 시켰을 때 흔히 겪는 문제 — 시키지도 않은 파일을 고치고,
막히면 조용히 다른 방법으로 돌아가고, 실행해보지도 않은 코드를 "됩니다"라고 보고하는 것 —
을 규칙과 절차로 막는다.

---

## 이게 뭔가

`에이전트 = 모델 + 하네스` 라고 할 때, 이 저장소는 **하네스 쪽**이다.
같은 모델이라도 어떤 규칙과 절차를 둘러주느냐에 따라 결과가 달라진다.

핵심은 `constitution.md` 한 파일이다. 이것이 `~/.claude/CLAUDE.md` 에 설치되어
모든 프로젝트의 세션에 적용되는 **전역 규칙**이 된다. `install.sh` 는 그 배포기다.

이 하네스가 최적화하는 것은 **정렬(alignment)** — AI가 사용자의 의도에서 벗어나지 않는 것이다.
자율성이나 속도가 아니다. **혼자 멀리 가는 것보다 같은 방향으로 가는 것이 우선이다.**

공개된 하네스 중에는 반대 방향(자율 최대화 — 사람을 부르지 않고 얼마나 멀리 가는가)을
최적화하는 것들이 있다. 목적 함수가 다르면 같은 부품을 써도 설계가 달라진다.
**둘 중 무엇이 옳다는 얘기가 아니라, 이 저장소는 전자를 고른 결과물이다.**

## 무엇이 달라지나

가장 큰 장치는 **변경 등급표**다. 에이전트가 무언가 하기 전에 스스로 등급을 판정한다.

| 등급 | 언제 | 에이전트의 행동 |
| --- | --- | --- |
| **A** | 합의한 설계 변경, 범위 밖 파일 수정, 새 의존성 추가, 막혔을 때의 우회, 되돌리기 어려운 것 | **멈추고 먼저 묻는다** |
| **B** | 합의된 범위 안의 구현 세부, 명백한 버그 수정, 오타 | 진행하되 완료 보고에 명시 |
| **C** | 읽기 전용 탐색, 실패한 시도의 되돌림 | 보고하지 않는다 |

**A인지 B인지 애매하면 A로 취급한다.** 애매함 자체가 방향성 위반의 신호이기 때문이다.

여기에 따라오는 규칙들:

- **제안은 살리고 실행은 막는다** — 시키지 않은 개선 아이디어는 버리지 않되, 실행하지 않고
  보고 끝에 "제안"으로만 남긴다. 좋은 아이디어와 방향 이탈을 동시에 해결한다.
- **사실과 추측을 구분한다** — 모든 판단에 `확인됨` / `추정` / `미확인` 을 붙인다.
  실행해본 것만 "동작한다"고 말한다.
- **모르면 질문한다** — 단, 선택지와 각각의 결과를 함께 제시한다. 열린 질문을 던지지 않는다.
- **막히면 우회하지 않는다** — 다른 방법으로 돌아가기 전에 막힌 지점부터 보고한다.

전체 규칙은 [`constitution.md`](constitution.md) 에 있다. 11개 절, 약 140줄이다.
**설치 전에 이 파일부터 읽는 것을 권한다** — 앞으로 모든 세션에 적용될 내용이다.

## 요구사항

- **Claude Code** (이 하네스는 `~/.claude/CLAUDE.md` 와 `~/.claude/skills/` 규약에 의존한다)
- `bash`, `python3`, 표준 유닉스 도구 (`cp`, `date`, `grep`)
- **macOS에서 개발·검증했다.** Linux는 미검증이지만 위 도구만 쓰므로 동작할 가능성이 높다 *(추정)*

## 설치

```bash
git clone https://github.com/nan-park/harness.git
cd harness
./install.sh
```

### 설치기가 하는 일

| 대상 | 무슨 일이 일어나나 |
| --- | --- |
| `~/.claude/CLAUDE.md` | 헌법을 `<!-- HARNESS BEGIN -->` ~ `<!-- HARNESS END -->` 마커 블록으로 넣는다. **기존 내용은 블록 아래에 그대로 보존된다.** 재실행하면 블록만 교체한다(멱등) |
| `~/.claude/CLAUDE.md.bak.<타임스탬프>` | 손대기 **전에** 원본을 백업한다. 매 실행마다 하나씩 쌓이니 가끔 정리하면 된다 |
| `~/.claude/skills/kickoff/` | `skills/` 아래 디렉터리를 복사한다. harness가 설치한 스킬만 자동 업데이트하며, 같은 이름의 사용자 스킬이 있으면 중단한다 |
| `~/.claude/harness/journal/drift-log.md` | 선택적으로 쓰는 이탈 장부. **없을 때만** 서식에서 만들고 제거 시에도 보존한다 |

설치와 제거는 동시에 하나만 실행된다. 이전 작업이 강제 종료되어
`~/.claude/.harness-install.lock`이 남았다면, 실행 중인 설치기가 없는지 확인한 뒤 그 디렉터리를
지우고 다시 실행한다. 설치 도중 실패하면 기존 파일을 복구하지만, 변경 전에 만든 백업은 안전을
위해 남긴다.

네 가지 모드가 있다:

```bash
./install.sh          # 마커 블록만 교체 — 기존 CLAUDE.md 내용 보존 (기본, 권장)
./install.sh --fresh  # CLAUDE.md가 없거나 빈 첫 설치용 (기존 내용이 있으면 중단)
./install.sh --verify # 헌법·스킬이 원본과 정확히 일치하는지 검사
./install.sh --uninstall # harness 소유 블록·스킬만 제거 (장부와 사용자 파일 보존)
```

설치 경로는 `CLAUDE_HOME` 환경 변수로 바꿀 수 있다(기본값 `~/.claude`). 장부를 포함한
런타임 데이터는 `HARNESS_DATA_DIR`로 따로 지정할 수 있다(기본값 `$CLAUDE_HOME/harness`).
**먼저 시험해보고 싶다면 진짜 설정을 건드리지 말고 이렇게 하면 된다:**

```bash
CLAUDE_HOME=/tmp/harness-test ./install.sh --fresh && cat /tmp/harness-test/CLAUDE.md
```

### 설치한 뒤 처음 쓰기

1. 실행 중인 Claude Code 세션이 있다면 닫고, 작업할 프로젝트에서 새 세션을 연다.
2. 프로젝트에 `CLAUDE.md`가 없거나 비어 있다면 `/kickoff`를 실행한다.
3. 목적·성공 기준·비목표 등의 질문에 답한다.
4. 에이전트가 보여주는 프로젝트 `CLAUDE.md`와 `PROGRESS.md` 초안을 확인하고 승인한다.
5. 이후에는 평소처럼 작업을 요청한다. 설치 상태가 의심되면 harness 저장소에서
   `./install.sh --verify`를 실행한다.

`/kickoff`는 강제가 아니다. 다만 생략하면 변경 등급표가 작업 범위 안과 밖을 판정할 기준이
부족해져 확인 질문이 늘거나 방향 이탈을 놓칠 수 있다.

### ⚠️ 설치 전에 확인할 것

- **`kickoff`라는 이름의 사용자 스킬이 있으면 설치기는 변경 전에 중단한다.** 기존 v0.1 설치본을
  새 관리 방식으로 전환하려면 `./install.sh --overwrite-skills`를 한 번 실행한다. 기존 디렉터리는
  `kickoff.bak.<타임스탬프>`로 백업된다. 저장소 안의 레거시 이탈 장부가 있으면 새 데이터 경로로
  복사하며 원본도 보존한다.
- **`--fresh`는 기존 `CLAUDE.md`가 없거나 비어 있을 때만 동작한다.** 기존 규칙이 있으면
  설치기가 중단하므로 기본 모드(`./install.sh`)를 사용한다.
- 헌법은 **모든 프로젝트의 모든 세션**에 적용된다. 특정 프로젝트에만 쓰고 싶다면
  `constitution.md` 내용을 그 프로젝트의 `CLAUDE.md` 에 직접 붙여넣는 편이 낫다.
- `~/.claude/CLAUDE.md` 에 이미 자기 규칙이 있다면 **헌법 블록 아래로 밀려나되 그대로 남는다.**
  충돌하면 헌법 §1 우선순위표를 따른다 — 자기 규칙은 5번이라 §2·§3의 핵심과 §8 안전 예외는
  못 덮어쓰지만, 그 밖의 헌법 기본값보다는 우선한다.

### 제거

다음 명령은 마커 블록과 harness 소유 표식이 있는 스킬만 제거한다. 사용자의 다른 규칙과
이탈 장부는 보존한다.

```bash
./install.sh --uninstall
```

## 구성

| 경로 | 무엇 | 배포 위치 |
| --- | --- | --- |
| `constitution.md` | 헌법 — 등급표, 사실/추측 구분, 질문·검증 규칙 | `~/.claude/CLAUDE.md` 의 마커 블록 |
| `skills/kickoff/` | 프로젝트 진입 인터뷰 절차 | `~/.claude/skills/kickoff/` |
| `journal/drift-log.template.md` | 이탈 기록 장부의 빈 서식 | `$HARNESS_DATA_DIR/journal/drift-log.md` 초기화에 사용 |
| `journal/changelog.md` | 어떤 실패로 어떤 규칙이 생겼는지 — 규칙의 근거 | — |
| `install.sh` | 배포기 (멱등) | — |

### `/kickoff` — 프로젝트 진입 인터뷰

등급표는 **"무엇이 범위 밖인가"** 를 알아야 작동한다. 그 기준선을 만드는 절차다.
`CLAUDE.md` 가 없는(또는 비어 있는) 프로젝트에서 세션을 시작하면 에이전트가 먼저 제안한다.

목적·성공 기준 / **비목표** / 고정값(언어·버전·라이브러리) / 산출물 위치 / 일정 /
프로젝트별 예외 규칙 / 참고 자료와 이탈 기록 동의 — 7가지를 나눠 묻고, 프로젝트 `CLAUDE.md` 와
`PROGRESS.md` 초안을 만들어 **승인받은 뒤에** 저장한다.

이 중 가장 중요한 것은 **비목표**다. 그게 없으면 "범위 밖 파일 수정"(등급 A ②)을 판정할 수 없다.

### 이탈 기록 (drift log)

이 하네스의 개선은 **감이 아니라 실제로 어긋난 기록**으로만 한다.
프로젝트 kickoff에서 사용자가 명시적으로 동의한 경우에만, 방향을 되돌리거나 재작업을
지시하면 에이전트가 그 자리에서 장부에 1행 남기고,
같은 유형이 3회 쌓이면 그때 개선안을 제안한다.

장부에는 실제 프로젝트명과 업무 내용이 들어간다. 그래서 기본값은 공개 저장소 밖인
`~/.claude/harness/` 아래다. 설치기는 파일이 없을 때만 만들며 재설치와 제거로 지우지 않는다.

여러 대의 컴퓨터에서 쓴다면 별도 프라이빗 저장소를 만든 뒤
`HARNESS_DATA_DIR=/path/to/private-repo ./install.sh`로 지정한다.

공개해도 되는 부분 — 어떤 실패가 관측되어 어떤 규칙이 바뀌었는지 — 은
[`journal/changelog.md`](journal/changelog.md) 에 따로 적는다. **규칙이 왜 지금 모습인지는 그 파일을 보면 된다.**

## 설계 원칙

1. **등급으로 나눈다** — 모든 변경을 사전 승인(A) / 사후 보고(B) / 무보고(C)로 분류한다.
   애매하면 A. 애매함 자체가 방향성 위반의 신호다.
2. **제안은 살리고 실행은 막는다** — 시키지 않은 개선 아이디어는 버리지 않는다.
   실행하지 않고 제안으로만 남긴다.
3. **근거 없이 고치지 않는다** — 하네스 개선은 이탈 기록으로만 한다. 감으로 만든 규칙은 과설계다.
4. **필요할 때 복잡해진다** — 최소로 시작하고, 관측된 실패가 요구할 때만 부품을 늘린다.
5. **훅은 증명된 뒤에** — 지시문으로 안 되는 것이 2회 이상 반복되면 그때 코드로 막는다.

## 내 것으로 고쳐 쓰기

이 저장소는 **한 사람의 작업 방식에 맞춰 만든 것**이다. 그대로 쓰기보다 고쳐 쓰길 권한다.

- 계속 업데이트를 받을 생각이라면 이 저장소를 **자기 GitHub 계정으로 포크하고 그 포크를 clone**한 뒤,
  포크의 `constitution.md`를 고치고 `./install.sh`를 다시 실행하는 방식을 권한다. 원본 저장소를
  직접 수정하면 나중에 `git pull`할 때 충돌할 수 있다.
- 원본 업데이트는 자기 포크에서 upstream 변경을 먼저 병합하고 내용을 검토한 뒤 `./install.sh`를
  다시 실행한다. 적용 후에는 `./install.sh --verify`로 확인한다.
- **`~/.claude/CLAUDE.md` 를 직접 고치지 않는다.** 다음 설치 때 사라진다. 항상 원본을 고친다.
- 헌법에서 `[조정 가능]` 으로 표시된 항목은 프로젝트별 `CLAUDE.md` 가 덮어쓸 수 있다.
  안전 예외(§8)와 등급표(§2)의 골격은 덮어쓸 수 없게 되어 있다 — 이 부분도 취향에 맞게 바꾸면 된다.
- 새 부품을 만들 때는 **어떤 실패 때문에 존재하는가**를 파일 상단에 적어두면,
  나중에 모델이 좋아졌을 때 그 부품의 제거를 검토할 목록이 된다.

## 한계 — 이걸로 막히지 않는 것

정직하게 적어둔다.

- **이건 프롬프트지 샌드박스가 아니다.** 규칙은 모델이 따르기로 한 약속일 뿐,
  강제 차단이 아니다. 실제 차단은 훅(v0.2)의 몫이고 아직 없다.
- **Claude Code의 권한 설정을 대체하지 않는다.** 파괴적 명령을 진짜로 막으려면
  Claude Code 자체의 권한 모드를 함께 쓴다.
- **매 세션 토큰을 더 쓴다.** 헌법이 항상 컨텍스트에 올라가고, 확인 질문이 늘어난다.
  속도가 목적이라면 이 하네스는 맞지 않는다.
- **효과를 정량으로 측정한 적이 없다.** 벤치마크 없이 실사용 경험으로만 다듬은 것이다.
- 헌법 안의 우선순위는 프롬프트 지침이며 Claude Code가 기술적으로 강제하는 권한 계층은 아니다.

## 이 저장소는 미러다

이 저장소는 **비공개 정본에서 허용목록으로 걸러 내보낸 사본**이다. 왜 정본을 따로 두는지는
위 "이탈 기록" 절과 같은 이유다 — 장부에 실제 업무 내용이 들어간다. 공개 범위를 저장소
경계가 아니라 **발행 시점의 허용목록**으로 옮겼을 뿐이다.

- 발행할 때마다 커밋 하나가 추가되고 메시지는 그때 새로 쓴다. 정본의 커밋 단위·메시지와
  일대일로 대응하지 않는다
- **히스토리를 다시 쓰지는 않는다.** 발행은 항상 커밋 추가이며 force push를 하지 않는다.
  위 "내 것으로 고쳐 쓰기"의 포크 후 upstream 병합 방식은 그대로 유효하다

## 기여

개인용으로 만든 것이라 정해진 기여 절차는 없다.
이슈로 의견을 남기는 것은 환영하지만, 반영 속도나 방향을 약속하지는 못한다.
포크해서 자기 것으로 만드는 쪽을 더 권한다.

**PR을 보내면 이 저장소에서 머지하지 않는다.** 미러이기 때문이다. 여기서 머지하면 다음
발행이 그것을 정본에 없는 커밋으로 감지해 멈추고, 정본에 반영되지 않은 변경은 그 뒤
발행에서 되돌아간다. 그래서 내용을 정본에 직접 반영한 뒤 PR에는 반영했다고 적고 닫는다.
번거롭게 해서 미안하지만 조용히 사라지는 것보다는 낫다고 본다.
